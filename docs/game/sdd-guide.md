# SDD 规范

本页说明**如何写**规格文档。
若你要往 [游戏规格](/game/) 里加内容，先读这页。

## 为什么要有规范

SDD 的价值取决于规格的**可追溯性**与**可执行性**。
如果规格只是散文，那它和 README 没区别。
规范让每一条规格都能被机器检查、被同事追溯、被任务承接。

## 三层与编号

```text
需求层  REQ-<域>-<序号>     玩家要什么
设计层  DES-<域>-<序号>     怎么做
任务层  T-<里程碑>-<序号>   谁在什么阶段做
```

**域**缩写：

| 缩写 | 含义 |
| --- | --- |
| `VIS` | 愿景 |
| `PLY` | 玩法 |
| `CHR` | 角色 |
| `STG` | 关卡 |
| `GDD` | 策划 |
| `NFR` | 非功能 |
| `ARCH` | 架构 |
| `MOD` | 模块 |
| `DATA` | 数据 |
| `CROSS` | 跨端 |
| `ART` | 美术 |
| `UX` | 交互 |

**编号规则**

- 三位序号，从 001 开始
- **一经发布不复用、不重排** —— 作废的需求标注「已作废」并指向替代编号
- 编号是稳定引用锚点，代码注释与 commit message 都可引用它

## 需求条目的必填字段

```markdown
| 编号 | 标题 | 优先级 | 验收 | 追溯 |
| --- | --- | --- | --- | --- |
| REQ-PLY-007 | 死亡后回到关卡起点，保留已拾武器 | P0 | 重试保留武器槽状态 | DES-MOD-004 |
```

**验收条件必须可判定**。「手感好」不合格；
「重试后武器槽状态与死亡前一致」合格。

**优先级**

| 级别 | 含义 | 判定 |
| --- | --- | --- |
| P0 | 必须有 | 没有它游戏无法成立或无法发布 |
| P1 | 应该有 | 缺失会明显损害体验，但不阻塞发布 |
| P2 | 可以有 | 锦上添花，可延后 |

## 需求层与设计层的分工

这是 SDD 最容易做错的地方。

| 写在需求层 | 写在设计层 |
| --- | --- |
| 「角色能跳跃」 | 「跳跃用 Phaser 的 Arcade Physics」 |
| 「Boss 有两个形态」 | 「Boss 用状态机，阶段由 HP 阈值驱动」 |
| 「关卡有 12 关」 | 「关卡数据存 JSON，由 StageRunner 加载」 |
| 「移动端也能玩」 | 「通过 game-platform 接口抽象，用 Capacitor 包装」 |

**判据**：需求层出现类名、文件名、框架名 = 写错地方了。

## 追溯链

```text
REQ-PLY-007  死亡后回到关卡起点，保留已拾武器
    │
    ▼  实现：REQ-PLY-007
DES-MOD-004  World 重置流程
    │
    ▼  实现：DES-MOD-004
T-M0-04      实现移动与跳跃（重置逻辑在此任务内）
```

**规则**

1. 每个设计条目在其文档末尾的「追溯」小节列出它实现的需求编号
2. 每个任务在其描述中列出追溯的需求/设计编号
3. **设计与任务若无法回指需求，说明它没有需求支撑** —— 应删除或补需求

## ADR 规则

任何**难以逆转**或**影响多个模块**的决策，都应写 ADR：

| 判据 | 说明 |
| --- | --- |
| 难以逆转 | 改了要重写大量代码（如换引擎、换状态管理方案） |
| 影响多模块 | 跨越了包边界（如规则层与渲染层的关系） |
| 代价非显然 | 好处容易看到，坏处要写出来 |

ADR 格式：**背景 → 决策 → 理由 → 代价 → 重新评估的触发条件**。

「重新评估的触发条件」是最容易漏、也最有价值的一栏 ——
它让未来的读者知道什么时候该重新考虑这个决策。

## 变更流程

```text
提出变更
  │
  ├─→ 判断影响面
  │     ├─ 需求变更？ → 改需求文档 → 更新编号 → 改受影响的设计 → 改受影响的任务
  │     ├─ 设计变更？ → 检查是否触发新 ADR → 改设计文档 → 改受影响的任务
  │     └─ 任务变更？ → 直接改任务文档
  │
  └─→ 全部改完后跑 pnpm verify（链接检查在构建期）
```

**顺序不可颠倒**：先改规格，再改实现。
反过来做，规格就会变成对实现的追认，失去约束力。

## 文档质量检查

提交前自查：

- [ ] 每条需求有唯一编号、优先级、可判定的验收条件
- [ ] 需求层没有出现类名、文件名、框架名
- [ ] 每个设计条目在末尾的「追溯」小节列出了需求编号
- [ ] 每个任务标注了追溯的需求/设计编号
- [ ] 内部链接可点通（VitePress 构建时检查，链接失效会直接构建失败）
- [ ] 新增页面已在 `config.mts` 的 `themeConfig.sidebar` 中登记

## 写作约定

- 中文正文用全角标点；代码、标识符、路径保持原样
- 每一页开头一句话说清「这一页解决什么问题」
- 表格用于对照类信息，列表用于流程与步骤
- 数字写明单位（180 px/s 而非 180）
- 不写「可能会」这类模糊表述，写清条件与结果
