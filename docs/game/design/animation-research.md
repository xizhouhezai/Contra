# 形象变体与骨骼动画调研

> 需求来源：用户提出「每个人物可选取不同形象（如 Q 萌版）」与「希望有骨骼运动，拿枪动作不同」
> 调研日期：2026-10-21 ｜ 状态：**待决策**

本文回答两个问题：

1. 多形象（立绘 / Q 萌版 / 表情差分）怎么组织；
2. 从静态贴图到「拿枪动作不同」需要什么技术，代价多大。

结论先说：**多形象可以立刻做，骨骼动画在本项目的素材条件下不成立**。
理由在第 4 节，有实测数据。

## 1. 素材现状（已核实）

仓库里已有的资源比预想的丰富：

| 类别 | 数量 | 规格 | 能否用于多形象 |
| --- | --- | --- | --- |
| 立绘 `portraits/` | 6 张 | 506×900、202×360、160×160 | ✅ 已接入选角界面 |
| 梗图 `official/meme-*/` | **57 张** | 202×360 ~ 360×360，Q 版 | ✅ 天然的「Q 萌版」 |
| ZipZipPipe 原始立绘 `zipzippipe/` | 20 张 | 全身立绘，含多个角色 | ✅ 备选形象 |
| 生成精灵表 `sprites/` | 34 张 | 48px 帧，4 状态 × 6 角色 + 10 敌人 | ⚠️ 占位，非真实美术 |
| 官方 PNG `official/*.png` | 3 张 | 豆包 3D 形象、logo | ⚠️ 商标素材 |

**57 张梗图是关键发现**：它们按角色分目录（`meme-deepseek/` 20 张、
`meme-qwen/` 6 张、`meme-kimi/` 6 张……），本身就是现成的 Q 萌版形象库。
不需要下载任何新素材。

> 尺寸实测：梗图**并非全是方形**，多数是 202×360 或 360×202 的竖幅/横幅，
> 少数 360×360。布局时不能假设正方形，宽高比需要按实际源图处理。

## 2. 多形象：可行的做法

### 2.1 形象维度

每个角色有两个正交维度可以独立选择：

| 维度 | 取值 | 来源 |
| --- | --- | --- |
| 形象 | 立绘 / Q 萌 | `portraits/` + `official/meme-*/` |
| 表情 | 常态 / 受伤 | 立绘（梗图表情另计） |

在选角界面做成「角色 → 形象」的二级选择：先选角色，再选该角色的形象。

### 2.2 数据结构

沿用现有的 manifest 模式，扩展为按角色聚合：

```ts
// packages/game-web/src/assets/manifest.ts
export interface CharacterVariant {
  /** 立绘的纹理 key */
  readonly key: string
  /** 展示名，如「立绘」「Q 萌」 */
  readonly label: string
  /** 源图尺寸，用于等比缩放 */
  readonly width: number
  readonly height: number
}

export function variantsFor(character: CharacterId): CharacterVariant[]
```

`variantsFor` 从 `import.meta.glob` 收集的结果里按角色聚合，
缺少某个形象时该形象不出现——**降级而不是报错**。

### 2.3 关键约束：素材来源必须一致

57 张梗图来自梗鲸档案馆，**各自作者不一、多数未声明许可**。
而 `portraits/` 是 ZipZipPipe（CC BY-NC-SA 4.0）或官方素材。

这意味着：**同一角色的两套形象可能来自不同作者**。
如果一个玩家把「立绘版」和「Q 萌版」混用，署名表要同时列出两位作者。

**处理方式**（不做技术判断，只记录约束）：

- 梗图单独建一个来源分组，署名表按「角色 → 形象 → 作者」列；
- 素材目录移入 `assets/variants/`，与 `assets/` 主体分开；
- 沿用现有的非商业前提（见[素材署名](/game/design/credits)）。

### 2.4 工作量估算

| 内容 | 规模 |
| --- | --- |
| manifest 扩展 `variantsFor` | 约 40 行 |
| 选角界面二级选择（形象切换） | 约 80 行 |
| 梗图 57 张重命名归档 | 脚本，约 30 行 |
| 立绘/梗图统一缩放与遮罩 | 约 60 行 |
| 单测 | 约 60 行 |

**总计约 270 行，一个里程碑内可完成。** 无外部依赖，无授权成本。

## 3. 骨骼动画：技术路线

调研了四条路线，可行性依次递减：

### 3.1 Spine（商业标准）

| 项 | 值 |
| --- | --- |
| 运行时 | `@esotericsoftware/spine-phaser-v3` |
| 版本要求 | Phaser ≥ 3.60（本项目 3.90 ✅） |
| 运行时授权 | Spine Runtimes License，需随游戏分发 |
| 编辑器 Essential | **$99** |
| 编辑器 Professional | **$449** |
| Enterprise | $500,000+ |
| 产物 | `.skel` + `.atlas` + `.png` |

集成方式清晰：

```ts
// main.ts
plugins: { scene: [{ key: 'spine.SpinePlugin', plugin: spine.SpinePlugin, mapping: 'spine' }] }

// BootScene.preload()
this.load.spineSkeleton('hero-skel', 'hero.skel')
this.load.spineAtlas('hero-atlas', 'hero.atlas')

// 场景
const hero = this.add.spine(x, y, 'hero-skel', 'hero-atlas')
hero.animationState.setAnimation(0, 'fire', false)
```

**Spine 的能力与需求完全对上**：骨骼层级、插槽换图（`Skin`）天然支持
「多套形象 + 不同动作」——换形象是换 skin，换动作是换 animation。

### 3.2 Rive

面向交互式矢量动画，状态机驱动，Web 运行时免费。
但它是**矢量路径动画**（`.riv`），导入位图需要先描摹成矢量，
对已有的 506×900 位图立绘是逆向工作，且会损失原画质感。

### 3.3 AI 自动绑定

2025 年的 UniRig（SIGGRAPH 2025）证明了单图自动提取骨骼可行。
但它输出的是 **3D 骨架**，面向的是 3D 角色，
且结果需要人工修整。对本项目而言，这等于「AI 出初稿 + 人工逐帧修」，
工作量不比手动画少，且引入不可控的中间产物。

### 3.4 剪纸动画（Cutout）

把角色切成头/身/手臂/腿几块，用代码做变换。
不需要专用编辑器，但**需要人工切图**——从 506×900 的立绘里
分离出干净的头和手臂，边缘处理比画骨骼更耗时。

## 4. 为什么骨骼动画在本项目不成立

这是本次调研最重要的结论，**不取决于技术难度，而取决于素材**。

### 4.1 现有美术无法被骨骼驱动

骨骼动画的前提是**素材本身由可分离的部件构成**。现状：

- `portraits/*.webp` 是**单张完整立绘**（506×900 的整幅插画），
  没有分层信息，骨骼无法从中「长出来」；
- `sprites/*.webp` 是**程序生成的 48px 色块**，
  有 4 帧（idle/run/jump/hurt）但没有可驱动的骨骼。

### 4.2 用 Spine 意味着重画全部角色

Spine 工作流是：

1. 在 Spine Editor 里**新建骨骼层级**（头/躯干/上臂/前臂/大腿/小腿…）；
2. 把美术**切成对应部件的 PNG**；
3. 逐个部件**对位到骨骼**；
4. 为每个动作（站立/跑/跳/受伤/开火/换弹）**K 帧**。

第 1、2 步对 6 个角色 × 2 套形象 = 12 套素材，
意味着 **12 次完整的拆件与绑定**。
按单套 2~4 小时估算，这是 **24~48 小时的人工美术工时**，
且第 2 步的切图会破坏原画（边缘会露出白边或糊掉）。

### 4.3 与「拿枪动作不同」这个具体需求的匹配度

需求说「拿枪动作不同」。但现在的游戏是**八方向射击的清版射击**，
玩家手里**没有枪械模型**，武器是抽象的光弹。

这一点在代码里是明确的：`packages/game-core/src/data/weapons.ts`
里十把武器全是 `projectile` / `thrown` / `beam` 类型，
角色是**赤手空拳**发射弹幕。

所以「拿枪动作」实际需要的是：

- 给武器加**可持握的模型**（10 把 × 12 套形象 = 120 个部件）；
- 为每个角色 K 6 个动作。

**这是从「角色立绘」升级到「带武器的横版动作游戏」的美术量级。**
Spine 只是让这个量级变得可管理，不是让它变小。

### 4.4 结论

| 路线 | 结论 |
| --- | --- |
| Spine | 技术可行，**但需先重画 12 套带武器的分件素材**，工时 24~48h |
| Rive | 位图转矢量是逆向工作，不推荐 |
| AI 自动绑定 | 输出 3D 骨架，仍需大量人工修整 |
| 剪纸动画 | 需人工切图，边缘质量难保证 |

**推荐路径：先做多形象（成本低、素材已够），骨骼动画列为独立里程碑，
前提是先决定「是否要做带武器的横版动作」。**

## 5. 中间路线：让动作变化的低成本做法

如果目标是「动起来」而非「骨骼动画」，有几条便宜得多的路：

### 5.1 程序化形变（推荐先做）

用 Phaser 的 `Mesh` 或简单的**变换叠加**做伪骨骼：

- 整张立绘做**呼吸缩放**（idle 时 Y 轴 ±1%）；
- 开火时**整体后坐**（短促位移 + 轻微旋转）；
- 受伤时**朱红闪烁 + 抖动**。

这些不需要任何新素材，代码量约 60 行，
视觉上能明显区别「静止的贴图」和「有动作的角色」。
当前 `ActorView` 已经是单向同步的结构，加变换层不破坏契约。

### 5.2 换帧剪纸（Q 萌版专用）

57 张梗图是**表情包**，通常同一张脸配不同表情。
如果把它们按表情分组，可以在受伤/开火时切换到对应的表情图，
实现「状态变化」而不需要骨骼。

分组是人工活：文件是数字编号（`007.webp`、`010.webp`），
没有角色内的表情标签，需要看图归类。57 张大约 1~2 小时。

### 5.3 部件化立绘（折中）

如果愿意为**一张**示范角色（比如 DeepSeek）拆出 5~6 个部件
（头/上半身/前臂/后臂/腿/枪），就可以验证剪纸方案的效果，
成本约 2 小时，产出可复用的技术验证。

### 已交付

| 层 | 内容 | 验收 |
| --- | --- | --- |
| L1 形象变体 | 选角界面按 Q 切换所选角色的形象，形象条显示进度 | 浏览器实测：DeepSeek 21 套形象可切换 |
| L2 程序化动效 | 呼吸 / 后坐 / 受伤抖动 / 移动倾斜 | 浏览器实测：待机时 scaleY 逐帧变化，移动时固定且有倾斜 |
| L3 自由瞄准 | InputState 增加可选 aim 向量 | 浏览器实测：瞄准角度 -21.3 度，非八方向 |

### 实施中的实测数据

| 项 | 数值 | 说明 |
| --- | --- | --- |
| 首包 | **1.55MB** | 远低于 8MB 预算（REQ-NFR-003） |
| 按需加载 | 6.86MB | 音乐 5.62MB + 梗图 1.27MB |
| 新增测试 | 33 个 | looks 12 + motion 14 + freeAim 7 |

**关键发现：梗图并非方形。** 实测为 202×360、360×202、360×360 混存，
且是 **VP8 格式无 alpha 通道**，无法抠掉背景。布局按「contain 适配 + 独立画框」处理。

**体积约束的教训**：57 张梗图全量预加载使产物达 8.41MB 超预算，
改为 `import.meta.glob` 非 eager 模式解决。校验脚本 `scripts/check-first-load.mjs`
按「首包 vs 按需」分别计量 —— 之前用整个 dist 目录判断是口径错误。

| Q4 | 本轮范围 | 多形象+动效 / 只多形象 / 只动效 | **多形象 + 程序化动效** —— 改动集中，一个里程碑 |

### 为什么 Q2 是关键

Q2 决定的是工作量是 **60 行**还是 **40 小时人工**，与技术难度无关。

- 若目标是「角色不再是一张静止贴图」→ 第 5 节的程序化形变就够；
- 若目标是「像横版动作游戏那样有持枪动作」→ 那是**一次美术产线的升级**，
  应当作为独立里程碑单独立项，而不是夹在功能需求里做。

### 若选 Q2 = A（推荐）

本轮可直接执行的清单：

| 内容 | 规模 | 说明 |
| --- | --- | --- |
| `variantsFor(character)` 聚合接口 | 约 40 行 | 扩展 `assets/manifest.ts` |
| 选角界面形象二级选择 | 约 80 行 | 选角色后再选形象 |
| 梗图 57 张归档与命名 | 脚本约 30 行 | 移入 `assets/variants/` |
| 立绘/梗图统一缩放与遮罩 | 约 60 行 | 梗图非方形，需按源图比例处理 |
| 程序化动效（呼吸/后坐/受伤） | 约 60 行 | 扩展 `ActorView`，不破坏单向契约 |
| 单测 | 约 60 行 | |
| **合计** | **约 330 行** | 无新依赖，无授权成本 |

### 若选 Q2 = B

独立立项，需要先回答：

1. 美术产出由谁做（AI 生成 + 人工修？还是外包？）；
2. Spine 授权买哪一档（Essential \$99 / Professional \$449）；
3. 现有立绘是否保留为「立绘形象」，与新素材并存；
4. 战斗形态是否改变（八方向射击 → 横版动作会改变整个规则层）。

第 4 点尤其重要：**横版动作会改变规则层的移动、瞄准、碰撞模型**，
不只是美术。这已经是 M0 架构决策（ADR-0003）的范围了。
