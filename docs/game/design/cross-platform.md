# 跨端策略

## 目标

**Web 端首发验证玩法，原生 App 复用全部玩法规则。**

移动端不做「降级移植」，而是**换表现层、留规则层**。
若移动端需要重写规则，说明规则层没做到位 —— 那是要修的架构问题，不是移植的难。

## 隔离边界

```text
┌───────────────────────────────────────────────┐
│  共享  @contra/game-core   纯 TS，零依赖       │
│  角色能力 / 武器 / 伤害 / 碰撞 / 关卡规则      │
│  Boss 状态机 / 得分 / 进度                    │
└───────────────────────────────────────────────┘
         ▲                        ▲
         │                        │
┌────────┴─────────┐   ┌──────────┴────────────┐
│ Web 表现层        │   │ 原生表现层（后续）      │
│ @contra/game-web  │   │ Godot / Unity / 原生    │
│ Phaser 3          │   │ 需重写                 │
└──────────────────┘   └───────────────────────┘
         ▲
         │
┌────────┴─────────┐
│ 适配层             │
│ @contra/game-      │
│ platform           │
│ Input / Storage / │
│ Audio / Lifecycle │
│ / Haptics         │
└──────────────────┘
```

## 平台能力矩阵

| 能力 | 接口 | Web 实现 | 原生实现（后续） |
| --- | --- | --- | --- |
| 输入 | `InputSource` | 键盘 + 鼠标 + 触屏 | 原生手势 + 手柄 |
| 存储 | `Storage` | localStorage | 文件系统 / Keychain |
| 音频 | `AudioPort` | Web Audio API | 原生音频引擎 |
| 生命周期 | `Lifecycle` | Page Visibility | App 前后台 |
| 触感 | `Haptics` | 空实现（可选 Vibration API） | 真实震动马达 |

**为什么单独抽一层**：
规则层不能直接调 `document.addEventListener` 或 `localStorage`，
否则换原生端时规则层就得改。把平台能力收敛成接口，
规则层只依赖接口，原生端只需写一套新实现。

## 移动端路径

### 阶段一 · 移动浏览器（首发包含）

同一套 Web 构建，加触屏控制层：

- 左侧虚拟摇杆（移动 + 8 向瞄准）
- 右侧按钮组（射击 / 跳 / 炸弹）
- 按钮大小 ≥ 44×44 px（REQ-NFR-013）
- 竖屏提示旋转为横屏
- 使用 Capacitor 或 PWA 包装为可安装应用

**这一阶段不需要任何规则层改动。**

### 阶段二 · 原生 App（后续）

```text
复用：@contra/game-core  100%
复用：关卡数据、角色数据、数值表  100%
重写：表现层（精灵、动画、音频、UI）
适配：输入、存储、生命周期、触感
```

**候选引擎**：

| 引擎 | 优势 | 代价 |
| --- | --- | --- |
| Godot 4 | GDScript 或 C# 写表现层；移动端导出成熟；体积小 | 团队需学习新引擎；与 TS 工具链不共享 |
| 原生（Swift / Kotlin） | 体验最佳、平台能力最全 | 两端各写一遍，工作量最大 |
| Flutter | 一套代码两端；UI 层能力强 | 2D 动作游戏手感需大量调优；包体偏大 |

**建议**：先 Godot 4 作为试金石 —— 若规则层接口设计得当，
一个表现层原型能在 2 周内跑通；若跑不通，说明规则层耦合了渲染，应当先修架构。

## 性能分级

同一套游戏在不同设备上按能力分档：

| 档位 | 判定 | 粒子 | 阴影 | 视差 | 纹理过滤 |
| --- | --- | --- | --- | --- | --- |
| 高 | 桌面独显 / 高端移动 | 全量 | 开 | 4 层 | 线性 |
| 中 | 集显 / 中端移动 | 半量 | 关 | 3 层 | 线性 |
| 低 | 低端移动 | 最小 | 关 | 2 层 | 最近邻 |

**降级只降表现，绝不降逻辑帧率**（支柱一 / REQ-NFR-001）。
自动检测：开局 3 秒平均帧率 → 选档 → 允许玩家手动覆盖。

## 输入抽象

规则层只认 `InputState`：

```ts
interface InputState {
  moveX: -1 | 0 | 1
  moveY: -1 | 0 | 1
  jump: boolean
  fire: boolean
  bomb: boolean
}
```

三种输入方案（键盘 / 触屏摇杆 / 手柄）都归一化到这个结构。
触屏摇杆同时产出 `moveX` 与 `moveY`，天然支持 8 向瞄准。

## 数据兼容

移动端与 Web 端共享存档结构（见 [数据模型](/game/design/data-model)）。
带 `version` 字段以便迁移。
原生端若引入云存档，需额外加密存储（Web 端不加密，
因为 localStorage 本就非安全边界，威胁模型不同）。

## 风险

| 风险 | 缓解 |
| --- | --- |
| 规则层被表现层污染 | Biome 导入限制 + CI 依赖扫描（见 [模块设计](/game/design/modules)） |
| 移动端性能不足 | 帧预算监控；表现分级降级；逻辑帧率不降 |
| 触屏操作精度差 | 摇杆死区 + 放大跳跃按钮；提供手感校准 |
| 原生移植工作被低估 | 阶段二先做 2 周原型验证接口可行性 |
| 双端存档格式分叉 | 单一 `SaveData` 定义，共享包引用 |
