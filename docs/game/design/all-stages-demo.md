# 十二关全流程录像（Midscene 视觉测试）

> 用 [Midscene](https://midscenejs.com) 视觉 Agent 驱动真实 Chrome 跑完**全部十二关**，
> 每一关都做视觉断言。**带声音**，从进第一关开始录。

> **这一版修掉了上一版的三个观感问题**，成因各不相同：
>
> 1. **开头 20 多秒不动** —— 录制脚本在同一趟里既玩又调视觉模型做断言，
>    每次断言都要等模型读完截图，人就一直站着。现在**测试与录制拆成两个脚本**，
>    录制这一趟完全不调模型
> 2. **掉进坑里很久不结束** —— 这是**游戏本身的缺陷**，不是录制问题。
>    已在 v0.25.2 修复，见下节
> 3. **与怪兽贴在一起** —— bot 的「保持距离」阈值写成 95/130px，
>    敌人走进这个窄带它就左右抖（读数 92、97、92、97 反复横跳）。
>    现在拉宽到 110/170，且**距离按两维算**——原来只算 X 轴，
>    在垂直关里把头顶 800px 以外的敌人算成「贴脸 20px」，
>    那就是它在垂直井卡死 30 秒的原因

## 这一版修掉的游戏缺陷

### 掉出地图后永远不结束

**这是真的 bug，不是录制效果**。复现：把角色推下平台，10 秒后到达 y=64227，
下坠速度涨到 12320px/s，而三颗心完好、关卡既不失败也不通关。屏幕上看就是
角色掉出画面再也不回来——这正是「掉到桥下面很久才死亡重置」的来源，
而且它连「很久」都不是：**它永远不会死**。

原因：`updateMovement` 只做平台碰撞，没有任何「掉出世界」的判定。
此前修过「玩家能走出地图右侧」，但那只夹住了水平边界，**坑从来没有代价**。

修法：以关卡最低平台 + 260px 作为坠落面，越过就扣一颗心并放回最后站立处；
心耗尽则判负。复活点只在**连续站立 8 步（约 0.13s）**后才更新——否则会把玩家
放回坑的边缘，一按方向键又掉，同一颗心被反复扣。

回归测试 `fallDeath.test.ts` 5 项：扣心、放回平台、耗尽判负、
站在地上不触发、界内深坑不触发。

## 仍然存在的局限（如实记录）

### 背景在水平方向重复

场景图是 1920px 宽的插图，关卡有 12000px 宽，所以近景层在水平方向**完全重复约 4 次**。
实测：把 `tilePositionX` 设为 0 与 1920 各截一张，像素差异只有 **0.05%**——一模一样。

这是「用一张插图铺满长关卡」的固有限制，不是平铺参数写错了。可选方向：

- **生成更宽的图**（每层 5760px 以上，或做成可无缝平铺）——需要重出 12 关 × 4 层美术
- 降低近景层的视差系数，让重复间隔变长——代价是纵深变浅，治标不治本

录制这一版**没有改动背景**，所以视频里的重复就是当前版本的真实样子。

### 垂直井（第 11 关）只展示、不通关

这一关是之字形下降的井，路线要读着走。实测「按住右 + 连续跳」能把角色带下三层、
然后撞墙；每一种反射式规则要么卡住、要么把它送进同一个坑直到心耗尽。

与其让视频花 40 秒记录一个 bot 解不开的平台谜题，这一关只展示 20 秒画面然后继续。
它是整套里唯一一个「看而不打」的关卡。

### 720p 而不是 1080p

1080p 下 screencast 只能抓到 **26.6fps**，720p 能到 **32.6fps**（中位帧间隔 17ms）。
「游戏进行得不连贯」是明确投诉，流畅度比分辨率重要，所以选 720p。
代价是背景被缩到 1280/1920 = 0.67，边缘偏软——这是权衡，不是疏忽。

## 机器人是怎么玩的

不是按固定脚本按键，而是**每帧读游戏状态再决策**：

- **躲避**：把每颗敌方子弹沿速度外推 0.35 秒，判断弹道是否穿过玩家身体；会穿过就跳起或侧移换道
- **跳跃**：前方 26px 内有平台挡路就跳
- **攻击**：追到距敌人 90px 停下并持续开火，太近（<60px）反而后退避免接触伤害
- **推进**：没有敌人就继续向右走，**直到关卡自己的宽度**（不是猜一个距离）

> 最后一条改过一次：初版在 x>2400 就停下，那只有整关的三分之一，
> 于是机器人从没走到中段小 Boss 面前。改成按关卡宽度判断后，
> 它能推进到 x≈7200。

## 音频是怎么进去的

CDP 的 `Page.startScreencast` **只传视频帧**，不含声音；这台机器也没有立体声混音
（loopback）设备，无法从系统层采音。

做法是在页面内挂一个 `MediaStreamDestination` 到 Phaser 的 Web Audio 图上：

```js
const ctx = game.sound.context
const dest = ctx.createMediaStreamDestination()
game.sound.destination.connect(dest)
new MediaRecorder(dest.stream, { mimeType: 'audio/webm;codecs=opus' })
```

录到的就是玩家听到的原始音频，没有环境噪音，也不需要虚拟声卡。

## 踩到的三个坑

### 1. 第一帧是白的，视觉断言因此误报

切换场景会拆掉旧场景、建新场景，中间有**大约三帧**画布是空的。
第一版在这段空窗里问模型「画面里有角色吗」，模型如实回答「没有」——
**它是对的，那一帧确实是空白页**。

修法不是加一个固定延时，而是等条件成立：

```js
await page.waitForFunction(() => {
  const s = window.__contraGame?.scene?.getScene('Stage')
  return !!s && !!s.world && s.world.steps > 5
}, { timeout: 30000, polling: 100 })
```

### 2. 断言问「画面中央偏左有角色吗」，五关因此误判

关卡 3 的角色在画面**中间偏右**，被断言判为失败——画面本身完全正常。
一个会在正确输出上失败的断言比没有断言更糟。

改成问「画面里有角色吗」（不问位置），并且**先问名字**再做位置判断：
让模型数「第 N 行第 M 列」它会差一格，而让它念名字再比对字符串没有这种失败模式。

### 3. 视频合成出来是 concat 列表的文本，不是画面

第一版用 ffmpeg 的 concat demuxer 读一个图片列表，得到的视频里
**显示的是列表文件的文字内容**——concat demuxer 默认把图片列表当文本流处理。

改用 image2 demuxer 按帧号序列读：

```bash
ffmpeg -framerate 56 -i frames/%05d.jpg -i audio.webm \
  -map 0:v:0 -map 1:a:0 -c:v libx264 -crf 30 -maxrate 800k \
  -c:a aac -b:a 96k -movflags +faststart out.mp4
```

### 4. 帧率写成 30，整个视频快了一倍

**这是最隐蔽的一个**：录屏是按显示器的合成速率交付帧的，本机约 **56fps**；
而合成时手写了 `-framerate 30`。于是 49957 帧被塞进 30fps 的容器，
**播放速度变成两倍**。

症状是：角色站着不动时画面在跳，进度条莫名其妙往前蹿——
而文件本身看不出任何问题，时长是对的、每一帧都是真画面、播放器也不报错。

修法是**从帧的时间戳算出真实帧率**，而不是猜一个常数：

```js
const measuredFps = frames.length / (totalMs / 1000)
```

### 5. `-shortest` 把视频尾巴砍掉了 19 秒

音轨比视频轨短（录音晚启动、早结束），`-shortest` 会按较短的一条截断，
50 秒的录制出来只有 31 秒——画面提前结束而时间轴还在走，
**这正是「进度条突然跳到几分钟后」的另一半原因**。

改成给音频补静音到视频长度：

```bash
-af apad -t 896.320
```

### 6. 验证工具本身错了，差点误判成「视频错位」

修完之后做逐帧比对，用 `-ss` 抽帧却报 48% 差异——看起来像还有 bug。
实际是：**`-ss` 在 15 分钟的视频上只会落在最近的关键帧**，
而游戏画面大量静止，关键帧间距很长，抽出来的自然不是那一帧。

改用 `-vf select=eq(n\,N)` 按帧号取，才逐帧对上（差异 0.00%~6.19%，
来自重编码噪声）。

> 教训：**一个会误报的验证工具，比没有验证工具更贵**。
> 上一处（断言问「中央偏左有角色」）也是同一类错误——
> 两者都差点让我把「工具写错了」当成「代码有问题」去改正确的东西。

## 复现

```bash
# 1. 构建并起预览
```
