# 架构决策记录（ADR）

ADR 记录**为什么**做某个决策，而不只是做了什么。
当后续有人想推翻某个决策时，这页让他先看到当时的约束与代价。

**格式**：背景 → 决策 → 理由 → 代价 → 重新评估的触发条件。

---

## ADR-0001 · 采用 SDD 规格驱动开发

**状态**：已采纳

**背景**

本项目同时包含「游戏玩法」与「工程规范」两条主线。
若文档只是内容载体而非契约，文档与实现必然分叉 —— 这是长期项目腐化的头号原因。

**决策**

采用 **Spec-Driven Development**：规格文档是唯一事实源，
按 需求 → 设计 → 任务 三层递进，每层条目有稳定编号并可向上追溯。

**理由**

- 变更影响面可计算：改一条玩法 → 定位受影响的设计 → 定位受影响的任务
- 需求编号不复用，提供稳定引用锚点
- 任务层可直接映射到 issue tracker

**代价**

- 前期投入文档编写时间（估算占首版工期 10~15%）
- 需要维护追溯关系，文档变多后更新成本上升

**重新评估的触发条件**

- 团队规模超过 5 人，文档维护成本超过收益
- 项目进入纯维护阶段，无新需求

## ADR-0002 · Web 端采用 Phaser 3 + TypeScript

**状态**：已采纳

**背景**

魂斗罗类型是 2D 横版卷轴跑轰。技术栈需与工作区现有工具链（TypeScript / Vite / Biome / vitest）协同，
且首发平台是 Web。

**决策**

Web 表现层使用 **Phaser 3 + TypeScript**。

**理由**

| 候选 | 评估 |
| --- | --- |
| Phaser 3 | ✓ 2D 横版最成熟的 Web 方案；场景/输入/物理内建；TS 支持完善 |
| PixiJS | ✗ 只做渲染，需自建游戏循环、场景、物理，量大易错 |
| Godot 4 | ✗ Web 导出为 30MB+ WASM，与「首包 ≤ 8MB」冲突；工具链不共享 |
| Rust/C++ + WASM | ✗ 迭代慢，团队门槛高，与文档站工具链割裂 |

**代价**

- Phaser 约 1.2MB（gzip 后约 400KB），占用首包预算
- 必须自行实现规则层物理（Phaser 物理与可复现性要求冲突）
- 不能使用 Phaser 生态的部分现成插件

**重新评估的触发条件**

- Web 端性能无法达标（连续 2 个月优化后仍 < 50fps）
- 团队已有 Godot 专家且愿意承担 WASM 体积代价

## ADR-0003 · 玩法规则与渲染完全解耦

**状态**：已采纳

**背景**

明确要求「扩展到 App 时使用独立技术隔离」。若规则与渲染耦合，换引擎等于重写游戏。

**决策**

拆三层，依赖严格单向：

```text
game-web (Phaser)  →  game-platform (接口)  →  game-core (纯 TS，零依赖)
```

`game-core` 的 `package.json` 依赖必须为空，源码不得 import 任何渲染或平台 API。
由 Biome `noRestrictedImports` + CI 脚本双重强制。

**理由**

- 规则层可脱离浏览器单测，测试速度与可靠性大幅提升
- 未来换引擎只需重写表现层
- 事件驱动的边界让表现层可以任意重放战斗过程

**代价**

- 需自己实现碰撞与空间哈希（不能直接用 Phaser 物理）
- 事件定义需要额外设计成本
- 表现层同步实体状态时有轻微延迟（1 帧内），需注意插值

**重新评估的触发条件**

- 永不。除非放弃原生 App 扩展目标。

## ADR-0004 · 美术采用二次元立绘 + 序列帧

**状态**：已采纳

**背景**

角色是拟人化的大模型「宠物娘」，需要强辨识度与性格表达；
同时类型要求魂斗罗式的横版跑轰操作。

**决策**

**立绘**（1200×1600）承担角色辨识度与性格表达，用于选角、角色卡、登场演出、结算；
**序列帧精灵**（32×48）承担游戏内表现。

**理由**

- 立绘能表达「宠物娘」的二次元特征，纯像素精灵做不到
- 精灵保持横版动作游戏的清晰度与包体效率
- 两者分工让每类资产都用在最能发挥它的地方

**代价**

- 两套资产的风格一致性需要人工把控
- 精灵帧数是产能瓶颈（尤其主角的跑动 6 帧）

**缓解**

主角全套制作，杂兵用 2 帧简化 + 位移补偿。

**重新评估的触发条件**

- 立绘产能成为 M4 关键路径瓶颈，且无法通过外包解决

## ADR-0005 · 单人为主，双人合作机制仅在数据层预留

**状态**：已采纳

**背景**

魂斗罗的招牌是本地双人合作。但首版做真双人需要：
第二个玩家输入方案、友军伤害规则、生命池模型、关卡难度重平衡。

**决策**

首发**仅单人**。但关卡宽度、敌人密度、Boss 弹幕按双人可过标准设计；
数据层预留合作相关配置项（生命池模式、友军伤害开关），首发不启用。

**理由**

- 单人体验必须完整 —— 双人不能成为通关前提
- 按双人标准设计关卡，单人通关时会略微偏易，容错友好
- 数据层预留成本极低，但保留了「日后加合作」的选项

**代价**

- 单人体验可能偏简单（需要额外的难度选项补偿，见 GDD §3.5）
- 若未来要开合作，仍需一轮关卡重平衡

**重新评估的触发条件**

- 单人难度曲线实测过平或过难
- 有明确的用户需求要求合作模式

## ADR-0006 · 武器采用 4 槽共享 + 角色专属初始武器

**状态**：已采纳

**背景**

角色差异化需要承载点。方案有二：共享槽位（操作统一）或独立武器栏（差异化更深）。

**决策**

所有角色共用 **4 个武器槽**，拾取替换当前槽；
角色差异由**初始武器 + 被动 + 炸弹技**三层承担。

**理由**

- 武器切换逻辑统一 = 上手速度与操作一致性得到保证
- 差异落在三个维度叠加，玩家能明显感到「这是六款不同的游戏」（支柱二）
- 独立武器栏会让 UI 与平衡复杂度翻倍，收益不成比例

**代价**

- 后期所有角色都能拿到全部 10 种武器，武器层面的角色差异会被稀释
- 角色数从 4 增至 6 后，武器池同步扩容（8 → 10 种），稀释速度略快

**缓解**

被动技能是永久性的角色标识，与武器无关；
每幕的武器投放节奏受控，不让所有武器在第 6 关前全部可得；
Kimi 与 Gemini 的初始武器（回溯弹、棱镜弹）本身与其被动机制绑定，
拿到也用不出同等效果，武器层差异不会被完全抹平。

**重新评估的触发条件**

- 数据显示玩家选角分布严重失衡（单角色 > 40%，见 GDD §6.1 成功指标）

## ADR-0007 · 可选角色扩充至 6 人

**状态**：已采纳

**背景**

首版规格定了 4 名可选角色（DeepSeek / Qwen / 豆包 / GLM）。随着社区二创素材
积累，Kimi 与 Gemini 的形象也已成型且辨识度足够 —— 补进可选角色池的边际成本很低。

**决策**

可选角色从 4 人扩至 **6 人**（新增 Kimi 月读、Gemini 双子），
与原有 4 人**并列**在选角界面，不做隐藏或解锁。
Boss 阵容**保持 4 形态不变**（Claude / GPT 各两形态）。

**理由**

- 6 人覆盖 6 种互不重叠的打法：清群、点杀、托管、续航、复利、穿透
- Kimi 的长上下文与 Gemini 的多模态填补了原本缺失的两个玩法维度
- 12 关 3 幕的关卡结构不必重算，每关从 6 人里选 1，选择感反而更强
- 选角界面 6 栏在桌面端一行放得下，不增加额外界面层级

**代价**

- 平衡工作增加一倍：6 套武器数值 + 6 组被动 + 6 个炸弹需分别调平
- 立绘与精灵的产能需求从 4 套涨到 6 套，直接压缩 M4 工期
- 选角分布的统计样本更分散，「无单一角色 > 40%」这条指标更难满足

**缓解**

- 每种打法都绑定了**对应模型的技术特性**，不是数值换皮，天然不易重叠
- 里程碑 M1 出口标准从「4 角色可区分」提高到「6 角色可区分」
- 立绘产能优先保证 6 名可选角色，Boss 立绘可复用战斗中的放大形态

**重新评估的触发条件**

- 实测某两个角色的手感高度重合（护城河不足，需要重做其中一个）
- 选角界面在 1280px 宽度下放不下 6 栏
- M4 立绘工期超出预算，需砍回 4 人
